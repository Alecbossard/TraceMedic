# Frozen evaluation protocol v1

Frozen before final agent prompt tuning. All 24 cases are authored synthetic bugs, not customer incidents. Odd IDs form development; even IDs are the 12 held-out cases. Case titles describe symptoms, not causes. `oracle.json` and this directory are inaccessible through the incident MCP server. `frozen_manifest.json` records input and oracle hashes. Regeneration invalidates previously published results.

Run deterministic, single-agent and multi-agent methods on the same 12 held-out cases. Run one repetition per case, then repeat case-08 (data) and case-20 (ambiguous) once per method to expose some variability: **14 runs per method, 42 total**. This small sample is a fixture comparison, not an estimate of production accuracy. Do not tune prompts on held-out results. Report any engineering repair after evaluation and rerun the entire comparison under a new result label.

The LLM methods use the same provider, model, seed 17, temperature 0, 18 model-call limit, 14 MCP-call limit and 1200 generated tokens per call. Both can use the same incident tools; the coordinator has only delegation/finalization tools. Contexts differ because the multi-agent roles exchange typed findings instead of conversation history. Actual calls, tokens and latency must be reported, including retries and errors. Local inference incurs no metered provider charge; hardware/electricity cost is **not measured**.

Scoring is deterministic, against the hidden expected mechanism and recorded evidence. A correct supported result needs all concept groups (case-insensitive alternatives per group) in the diagnosis and a confirmed hypothesis, at least one valid file/line citation, and an actual completed fixture verification. Citation validity and execution are necessary but do not prove semantic entailment: keyword scoring has false-positive and false-negative risk; publish every run for inspection. A supported finding must not claim a repair was applied. Ambiguous cases must conclude `insufficient` and have no confirmed cause. A `supported` conclusion failing correctness/support checks is counted as an unsupported conclusion. Publish abstention, tool success, latency, calls and provider-reported tokens. Missing usage/cost stays null, never estimated. Error/budget outcomes count as failures, not exclusions.

Measure crash recovery separately with process termination and identical run IDs, evidence IDs and operation keys; compare executions before/after. Include deterministic-provider integration and real-model recovery explicitly as different evidence classes. Report all failures and overhead, regardless of which method wins.
